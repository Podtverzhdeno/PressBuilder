# tasks.md — PressBuilder: производство видео силами независимых агентов

Дата постановки: 2026-11-01. Владелец: координатор проекта. Ветка: `feat/cloud-mcp-video-editor-20261101`.
**Цель:** шесть независимых AI-агентов читают проект через MCP, создают технически полноценные 3D-сцены длительностью 3–7 секунд, проверяют каждую отдельно и передают на детерминированную сборку общего ролика.

## Принципы исполнения

1. Реализовывать **строго в порядке P01 → P10**, кроме исправления блокирующих ошибок и обязательных зависимостей.
2. Не считать спецификацию реализацией: пункт закрывается только при наличии API/кода, тестов, инструкции, воспроизводимого результата и подтверждённого CI.
3. Начинать с минимального вертикального среза функции, затем расширять его до заявленного Definition of Done (DoD).
4. Не изменять без необходимости чужие видео, пользовательские `deck.json` или общие библиотеки. Статус/чекпоинт нельзя проставлять «готово» по одному успешному запросу.
5. Для каждой сцены единый `scene_id`, отдельное хранилище исходников/артефактов и проверяемая ревизия. После отмены или падения попытка должна восстанавливаться без потери предыдущего принятого MP4.
6. Модель угроз: незнакомый агент может быть ошибочным/враждебным; входные JSON, ассеты, Markdown и произвольный код нельзя автоматически исполнять на Railway. У рендерера лимиты времени, памяти, числа объектов и размера файлов.
7. Текущие возможности: `get_project_context`, README, `get_scene_task`, чекпоинты и статусы; `set_slide_visuals` — простая 2D-графика, статические 3D-меши работают через код в репозитории, `render_video` использует одну глобальную очередь.
8. Если задача находится в процессе, указывать точный реализованный подэтап. Не переименовывать MVP в production-ready без соответствующих тестов.

## P01 — полноценный 3D Scene SDK и публикация сцен через MCP

**Проблема:** `set_slide_visuals` создаёт только плоские графические примитивы, а сложные 3D-сцены из примера `gameready-3d` требуют ручного изменения `src/decks/<id>/index.ts` и нового деплоя. Из отдельного чата агент не может передать своему слайду безопасную 3D-композицию.

**Продуктовая цель:** безопасно создавать одну 3D-сцену без правки чужих роликов, сохранять её в проекте, открыть/просмотреть/отрендерить через тот же Chromium-рендер.

**Декомпозиция:**
- [x] **P01.1 — Declarative 3D MVP.** Ограниченная JSON-сцена с 3D-мешами `cube/octa/icosa/hexPrism/cylinder`, положение `[x,y,z]`, масштаб, углы, скорость вращения, индивидуальные цвета/рёбра, камера `yaw/pitch/size/dist` и её скорость. Число объектов, координаты, размер/сложность и скорость ограничить. Никакого JavaScript/eval из MCP.
- [x] **P01.2 — Scene-scoped storage/API.** `GET/PUT /api/decks/:id/scene3d/:slide_id`, оптимистичная ревизия, атомарная запись в отдельный JSON на `/data`, idempotent reads и документация.
- [x] **P01.3 — MCP.** `get_scene_3d` и `set_scene_3d` с минимально-необходимыми правами и точной схемой. Не позволять выбирать чужой/несуществующий слайд; не менять `deck.json`.
- [x] **P01.4 — Runtime integration.** Загрузка данных в `src/decks/registry.ts`/timeline; 3D-шейдинг и перспектива через существующий `drawSolid`, `drawWire` и детерминированную функцию от `t`; корректная работа предпросмотра и Chromium-рендера. Поддержать кодовые сцены с явным порядком приоритета.
- [ ] **P01.5 — Production SDK.** Поддержка glTF/GLB/других ассетов с проверкой размера, MIME, хэша, лицензии, сканированием, реестром и сборкой. Отдельная архитектура публикации сложных TypeScript-сцен через доверенный CI/PR, **не** через выполнение произвольного кода пользователя на сервере.
- [x] **P01.6 — UI (MVP JSON editor; visual node-based builder remains future work).** Отдельная вкладка/визуальный конструктор 3D-сцены, предпросмотр, сохранение версии, fallback при отсутствии ресурсов.
- [ ] **P01.7 — Приёмка.** Интеграционный тест MCP→запись→чтение→рендер; реальная ненулевая 3D-анимация минимум двух вращающихся объектов, корректный FPS, невозможность path traversal, отклонение NaN/Infinity/oversized payload/постороннего slide ID; отсутствие изменений соседних сцен.
- **MVP exit:** агент в отдельном чате вызывает `set_scene_3d`, видит объекты в проекте, может сохранить и отрендерить сцену. **Full DoD:** отдельные GLB-ассеты и передача сложного сценового кода через проверяемую сборку.
- **Риски:** 3D-псевдорендер Canvas не равен полноценному WebGL; glTF требует отдельного безопасного пайплайна, 3D-меши с неограниченными полигонами недопустимы.
- **Оценка:** 10/10; приносит возможность, без которой другие стадии не дадут целевого качества.

## P02 — независимый рендер + очередь заданий

**Проблема:** серверный `render_video` использует глобальный `busy`; шесть агентов не могут независимо получать MP4 своих сцен.

- [x] **P02.1** `render_scene({id,slide_id,revision?})`, точный тайм-код начала/конца из расписания; аудио с корректным offset.
- [ ] **P02.2** (одноузловая FIFO реализована, долговременная очередь/worker pool не готовы) Job queue c состояниями `queued/running/completed/failed/cancelled`, идентификатором job_id, лимитом параллелизма, fair scheduling.
- [ ] **P02.3** Несколько workers или ограниченный pool; Railway CPU/RAM измерить нагрузочным экспериментом, не обещать 6 одновременных Chromium на одном сервере.
- [ ] **P02.4** Тайм-ауты, retries с backoff, отмена, восстановление после перезапуска, контроль повторных задач по content hash.
- [x] **P02.5** API `get_scene_render_status`, ссылки на MP4/превью, технические метаданные (codec/fps/duration/bytes).
- [ ] **P02.6** Тест: 6 запросов, 2+ разных сцен, один намеренно плохой job, отсутствие блокировки успешных; перезапуск worker не теряет запись о заданиях.
- **DoD:** каждый агент может проверить только свою сцену; ошибка одного job не влияет на другие.
- **Риски:** кодовые сцены зависят от единой timeline, поэтому корректно рассчитывать offsets/фейды; временное хранилище очищать безопасно.
- **Оценка:** 9.8/10.

## P03 — автоматический Video QA

**Проблема:** искажения шрифта, наложения объектов и пустые кадры обнаруживаются вручную после длительного рендера.

- [ ] **P03.1** Извлекать репрезентативные кадры: начало, 25%, 50%, 75%, конец, а также моменты появления объектов/реплик.
- [ ] **P03.2** Проверка формата (ffprobe), чёрных/битых кадров, резких скачков яркости, отсутствия звука при обязательной озвучке.
- [ ] **P03.3** Проверка геометрии: текст вне safe area, наложения крупных текстовых bbox, недопустимый horizontal compression, отсутствующие требуемые элементы.
- [ ] **P03.4** Регрессионные снимки / golden images с порогами для предсказуемых сцен; отчёты без ложного «художественного балла».
- [x] **P03.5** MCP `get_scene_qa_report`, вердикты PASS/REVIEW/FAIL и evidence (кадр+тайм-код+правило).
- [ ] **P03.6** Тестовые дефекты: намеренно обрезанный заголовок, полностью чёрный кадр и некорректный FPS должны ловиться; живые сцены не должны массово давать false positive.
- **DoD:** автоматические *технические* проверки работают без ручного просмотра; художественная приёмка остаётся за человеком.
- **Риски:** без контроля false positives QA станет блокировать хорошие анимации.
- **Оценка:** 9.7/10.

- [ ] **P05.2** Виды transition: hard-cut/match-cut/crossfade/morph-like; согласование длительности и стыка реплик.

- **Риски:** match-cut требует содержательных метаданных и ручной коррекции по композиции.

- [ ] **P06.1 (MVP: отдельные bearer keys, scoped roles; issuer/principal ещё нет)** Agent identity, roles `viewer/worker/reviewer/director` с привязкой к issuer/principal.

### P04–P06: пределы реализованного среза

- **P04:** проектный контракт хранится отдельно, default `enforce:false` сохраняет совместимость. Поддержаны MCP get/set и ограниченная проверка новых 3D/2D-публикаций; без schema-engine, scene overrides и реального визуального QA.
- **P05:** только детерминированный hard-cut H.264/AAC (нужны статус задачи `done`, QA PASS и сцены в порядке проекта). Нет crossfade/match cut, durable jobs или immutable аудита каждого рендера.
- **P06:** отдельные scoped bearer keys для workers/reviewers/viewers, fenced TTL lease и аудит. Общий MCP_API_KEY/OAuth/Basic — **директор**, а не отдельный агент. Вся модель рассчитана на один процесс и не защищает от злоупотребления директором. См. [docs/production-p04-p06.md](docs/production-p04-p06.md).
