# P02 + P03 — надёжные сценовые рендеры и проверяемое качество

Реализация в ветке `feat/p02-p03-production-hardening-20261101` / Draft PR #2. Основные компоненты: `server/render-queue.mjs`, `server/render.mjs`, `server/video-qa.mjs`, `src/engine/visual-qa.ts`.

## P02: безопасная очередь и выпуск MP4

### Контракт MCP

- `render_scene({"id":"film","slide_id":"s01"})` — создаёт задание и возвращает `job_id`/статус. Повторное обращение к той же ещё выполняющейся сцене возвращает **то же** задание.
- `get_scene_render_status({"id":"film","slide_id":"s01"})` — показывает статус `queued/running/cancelling/completed/failed/cancelled`, прогресс, ссылку и QA-отчёт.
- `cancel_scene_render({"id":"film","slide_id":"s01","job_id":"..."})` — отменяет только конкретную попытку. При `queued` убирает её из очереди; при `running` прекращает Chromium/CDP и FFmpeg через `AbortSignal`.
- `retry_scene_render({"id":"film","slide_id":"s01","job_id":"..."})` — явный повтор после завершённой/ошибочной/отменённой попытки. Отвергает устаревший ID. `render_scene` также может начать новую попытку без ссылки на старую.
- `cancel_video_render({"id":"film","job_id":"..."})` — отменяет полный ролик, не трогая прошлую принятую версию.
- Старые `render_video` и `get_render_status` остаются доступными.

### Защита от потери результатов

1. Каждая попытка рендера получает случайный `job_id`, собственный `out/<project>_<scene>_<job_id>.mp4` и файл состояния `/data/render-jobs/<SHA256(key)>.json`.
2. Текущее состояние сохраняется **атомарно**, а прогресс — каждые ~10%. Отдельное задание не перезаписывает соседние.
3. При рестарте Railway новые `queued/running` задания восстанавливаются (не более двух рестартов). Старые журналы прошлой версии мигрируют: проверенные завершённые MP4 сохраняются; старые активные задачи завершаются явной ошибкой, поскольку у них отсутствовал отпечаток исходников. `cancelling` завершается как `cancelled`; при повторных падениях фиксируется `failed` — бесконечного цикла нет.
4. Перед и после рендера сравнивается SHA-256 **всего таймлайна проекта**, 3D-описания выбранной сцены, style contract, идентификатора скомпилированного движка и метаданных аудио. Это предотвращает принятие результата после изменения соседних сцен, которое меняет расчёт времени. Если входные данные изменились, устаревший результат **не принимается**.
5. Новый MP4 становится доступен как принятый **только после PASS/REVIEW QA**. Поддерживается совместимый URL `/out/<project>_<scene>.mp4` — он атомарно обновляется только после успешной проверки. При неудаче/отмене предыдущий MP4 остаётся доступен, а неподтверждённый файл удаляется.
6. Очередь ограничена 50 ожидающими работами и **одним** тяжёлым worker на процесс. Есть максимальный тайм-аут одной запущенной задачи (по умолчанию 60 минут): превышение приводит к `failed`, а не к ложному `cancelled`. Некорректный/пустой ответ QA всегда означает отказ в публикации. Шесть запросов могут быть приняты, но выполняются последовательно.

**Безопасность:** worker должен предварительно получить lease своей сцены и передавать `fence_token` при `render_scene`, `cancel_scene_render`, `retry_scene_render`; директор имеет отдельное право управлять сценами. Viewer/reviewer не могут выполнять эти действия.

**Важно:** это не распределённая очередь с exactly-once семантикой. Несколько Railway-реплик с общим томом пока запрещены; для multi-instance нужны PostgreSQL-backed claim/lease/fencing. Входы кодовых сцен из CI также необходимо версионировать отдельно (P08). `cancel` завершается с небольшой задержкой во время отдельных CDP-вызовов.

- иммутабельные MP4 и совместимый «последний принятый» URL;
- сохранность старого MP4 после нового QA FAIL;

`tests/render-smoke.mjs` — Docker, HTTP/MCP, Chromium, FFmpeg, реальный MP4 и отчёты QA.

## P03: технический и ограниченный визуальный QA

### Проверки

| Вид | Инструмент | Автоматическое решение |
|---|---|---|
| Кодек, разрешение, FPS, длительность, аудио | `ffprobe` | `FAIL` при нарушении |
| Текст не помещается даже в шрифте 24px | Canvas `measureText` + реальная гарнитура | `FAIL` |
| Текст частично выходит за кадр | Позиция + фактическая измеренная ширина + scale | `FAIL` |
| Текст близко к краю, уменьшается на >40%, пересекается | Расчёт bbox | `REVIEW` |
| Все 3 выборочных кадра почти чёрные | 64×36 Canvas luminance | `FAIL` |
| Отдельный почти чёрный кадр | Canvas luminance | `REVIEW` |
| Ошибка исходных данных или FFmpeg | Проверяемый код ошибки | `FAIL` |

Сэмплируются три фактических кадра с относительными временными отметками 22%, 50%, 78% выбранного клипа. `REVIEW` — не блокирует запись MP4, но требует человека; `FAIL` блокирует признание результата успешным. Отчёт сохраняется вместе с job и доступен через `get_scene_qa_report` и `get_video_qa_report`.

Геометрия текста переводится в фактические координаты кадра с учётом сжатия сцены движком и нижнего безопасного поля; иначе возникают ложные FAIL по краям. Проверка текста распространяется **только на data-driven visuals**. Кодовые 3D-сцены и художественная композиция **не оцениваются автоматически**; в отчёте перечислены `uninspected_scenes`. Приоритет сцены учитывается, чтобы спрятанные data visuals не давали ложных дефектов. Учитываются пользовательские правки `objects`: текст, позиция, масштаб и `hidden`.

### Тесты P03

`tests/cloud-visual-qa.test.mjs` проверяет реальные метрики текста на имитированном Canvas, пересечение, обрезку, скрытые элементы, все-чёрный клип и безопасный `REVIEW`. `tests/cloud-video-qa.test.mjs` подтверждает технические дефекты.
