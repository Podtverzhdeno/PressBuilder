# P02 — Рендер отдельных сцен и очередь задач (MVP)

Реализован **in-process FIFO на одном worker**. Заявки шести агентов принимаются независимо, один Chromium-рендер выполняется за раз; остальные стоят в очереди, а не получают ошибку занятости. Это не параллельный рендер шести Chromium-процессов.

## MCP

- `render_scene({"id":"my-video","slide_id":"s03"})` — принимает задачу, возвращает `{id,slide_id,job_id,status:"queued"|"running",...}`.
- `get_scene_render_status({"id":"my-video","slide_id":"s03"})` — возвращает `queued/running/completed/failed`, процент `progress` и `result.download_url` для готового MP4.
- `render_video({"id":"my-video"})` / `get_render_status` продолжают работать для полного ролика; они используют ту же FIFO.
- Повторное обращение при `queued/running` возвращает тот же активный job вместо запуска дубликата; после завершения можно запросить новый рендер.

## Результат

Рендер использует фактическое расписание `buildSchedule`: диапазон сцены `[slide.start, slide.start+slide.dur)`. Кадры подаются в Chromium как `window.__PB_CLOUD_FRAME__(slide.start + frame/fps)`. Аудио дорожка (если есть) обрезается со смещением относительно её начала. Имя файла — `out/<project>_<slide>.mp4`; полный проект — `out/<project>.mp4`.

**Текущие ограничения и риски:**
- Очередь и состояния сохраняются в `/data/render-jobs/<sha256>.json`; задания в `queued/running` восстанавливаются после рестарта (максимум две попытки), прогресс сохраняется примерно каждые 10%. Это **MVP восстановления**, но ещё не распределённая durable-очередь с exactly-once гарантиями.
- Работает только один worker. Для настоящего параллелизма нужен процессный/контейнерный worker pool с CPU/RAM quota (P02.3).
- Нет отдельного `cancel`, ручного `retry`, структурированной истории попыток, многопроцессных блокировок или immutable версий результата (P02.4/P08).
- Новый рендер перезаписывает MP4 по старому URL — для принятых сцен требуется immutable storage (P08).
- Имя агента в задании пока не является техническим ACL; права вводятся в P06.
- Уровень звука и точность сдвига проверять на реальном речевом аудио в дополнительных тестах.
- Предел до 50 ожидающих работ и 10 минут на один clip, FPS 24/25/30/50/60.

## Проверки

`tests/render-smoke.mjs` запускается в Docker в PR CI, создаёт 3D-сцену из MCP, затем одновременно запрашивает полный MP4 и отдельный MP4 сцены. Проверяет, что оба job приняты, завершаются и оба результата скачиваются.

**DoD P02 пока не достигнут полностью:** несмотря на файловое сохранение и возобновление задач, требуются отмена, повтор по политике, наблюдаемость, отдельные workers, измерение CPU/RAM и независимое моделирование отказов.

## Один ресурсный слот и P08 scene cache (2026-11-01)

В cloud одна общая FIFO-квота `createResourceGovernor({capacity:1})` резервируется для Chrome+FFmpeg render P02 и FFmpeg montage P05. Вторая операция ожидает слот, не запускает параллельный тяжёлый процесс; ожидающий P05 может быть отменён и не создаст release. Отмена снимает waiter без утечки и позволяет следующему запросу продолжить работу. `resource_wait_ms` (render) и `timings_ms.wait_resource` (assembly) отражают ожидание. Это **in-process** лимит, а не distributed semaphore, и он не ограничивает аппаратную память для отдельных этапов.

При `render_scene` с неизменным полным отпечатком исходников (таймлайн, звук, сцены, 3D, стиль, renderer build, P08 snapshot) сервер ищет свежую P08 версию с `render_fingerprint`, `qa.verdict=PASS`, без открытых P07 замечаний. Проверяются SHA-256 MP4, три JPEG (если есть) и архив исходников. При успехе API сразу возвращает `cache_hit:true`, оригинальный `job_id` и новый `request_id`. Утверждённая P08 версия не меняется. `retry_scene_render` всегда принудительно создаёт новый render. Старые архивы без `render_fingerprint` не кэшируются. Повреждённые записи пропускаются, вместо выдачи невалидного MP4.

Не применяйте governor к нескольким репликам: для масштабирования нужны DB lease/fencing и object storage.

## P12 — быстрый предпросмотр черновой сцены

В облачной панели «Ревью MP4» новая кнопка «Создать предпросмотр (3 кадра)» получает реальные Canvas PNG с позиции 10/50/90% из Chromium, без кодирования H.264/AAC и без P08 version capture. Отдельные HTTP маршруты под Basic auth: `POST /api/decks/:id/preview/:scene`, `GET /api/decks/:id/preview/:scene`, `POST /api/decks/:id/preview/:scene/cancel`, `GET /api/decks/:id/preview/:scene/:index.png`. MCP-инструменты: `preview_scene` (worker с fenced lease / director), `get_scene_preview` (scoped read), `cancel_scene_preview`.

Черновой PNG помечается `DRAFT_FRAMES_ONLY`: это **не** P03 QA и не подтверждённый MP4. Каждый результат привязан к полному P02 source/build fingerprint, 3 PNG сохраняются в `/data/out/previews/:id/:scene/:fingerprint/` с SHA-256, pointer переключается после окончания записи. При изменении исходников картинки считаются устаревшими. Повторный запрос с тем же полным fingerprint берёт проверенный кэш, а повреждённые PNG не переиспользуются. Ресурсный слот делится с Chromium render, FFmpeg montage и P11 diff. В этой версии предпросмотр — один активный job на сцену, без постоянного журнала задач; после рестарта завершённый кэш сохраняется, незавершённый job требует запуска заново. Поведение проверяется в Docker smoke на реальном Chromium.

Ссылки на draft PNG и P11 diff в облачном API выдаются в same-origin виде `/api/...` или `/out/...`, чтобы редактор не зависел от настройки `PUBLIC_URL` и не пытался загрузить localhost-ссылку с удалённого хоста. MCP-клиент может разрешить относительный путь относительно своего PressBuilder endpoint; Basic авторизация всё равно обязательна.
