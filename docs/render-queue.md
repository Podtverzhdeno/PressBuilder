# P02 — Рендер отдельных сцен и очередь задач (MVP)

Реализован **in-process FIFO на одном worker**. Заявки шести агентов принимаются независимо, один Chromium-рендер выполняется за раз; остальные стоят в очереди, а не получают ошибку занятости. Это не параллельный рендер шести Chromium-процессов.

## MCP

- `render_scene({"id":"my-video","slide_id":"s03"})` — принимает задачу, возвращает `{id,slide_id,job_id,status:"queued"|"running",...}`.
- `get_scene_render_status({"id":"my-video","slide_id":"s03"})` — возвращает `queued/running/completed/failed`, процент `progress` и `result.download_url` для готового MP4.
- `render_video({"id":"my-video"})` / `get_render_status` продолжают работать для полного ролика; они используют ту же FIFO.
- Повторное обращение при `queued/running` возвращает тот же активный job вместо запуска дубликата; после завершения можно запросить новый рендер.

## Результат

Рендер использует фактическое расписание `buildSchedule`: диапазон сцены `[slide.start, slide.start+slide.dur)`. Кадры подаются в Chromium как `window.__PB_CLOUD_FRAME__(slide.start + frame/fps)`. Аудио дорожка (если есть) обрезается со смещением относительно её начала. Имя файла — `out/<project>_<slide>.mp4`; полный проект — `out/<project>.mp4`.

**Текущие ограничения и риски:**
- Очередь и состояния сохраняются в `/data/render-jobs/<sha256>.json`; задания в `queued/running` восстанавливаются после рестарта (максимум две попытки), прогресс сохраняется примерно каждые 10%. Это **MVP восстановления**, но ещё не распределённая durable-очередь с exactly-once гарантиями.
- Работает только один worker. Для настоящего параллелизма нужен процессный/контейнерный worker pool с CPU/RAM quota (P02.3).
- Нет отдельного `cancel`, ручного `retry`, структурированной истории попыток, многопроцессных блокировок или immutable версий результата (P02.4/P08).
- Новый рендер перезаписывает MP4 по старому URL — для принятых сцен требуется immutable storage (P08).
- Имя агента в задании пока не является техническим ACL; права вводятся в P06.
- Уровень звука и точность сдвига проверять на реальном речевом аудио в дополнительных тестах.
- Предел до 50 ожидающих работ и 10 минут на один clip, FPS 24/25/30/50/60.

## Проверки

`tests/render-smoke.mjs` запускается в Docker в PR CI, создаёт 3D-сцену из MCP, затем одновременно запрашивает полный MP4 и отдельный MP4 сцены. Проверяет, что оба job приняты, завершаются и оба результата скачиваются.

**DoD P02 пока не достигнут полностью:** несмотря на файловое сохранение и возобновление задач, требуются отмена, повтор по политике, наблюдаемость, отдельные workers, измерение CPU/RAM и независимое моделирование отказов.
