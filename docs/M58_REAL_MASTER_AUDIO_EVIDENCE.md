# M58-R20 — проверка реального MP4 по SHA и аудиоканалам (review-only)

**Состояние: изолированный серверный модуль, не развёрнут и не привязан к
production UI.** Начальная цель — отличить настоящий декодированный MP4 от
фикстуры с известным 110/440 Гц тоном в PR #50–51. M51-R03 (PR #53)
остаётся отдельной экспериментальной веткой для синтетических данных.

## Анализ и граница доверия

`inspectCurrentMasterStereo({assembly,projectId})` выбирает MP4 **только**
через существующие серверные `assembly.current(projectId)` и
`assembly.download(projectId,release_id)`. Пути/команды из HTTP-поля
пользователя не принимаются. `download` в P05 повторно проверяет байты
master по SHA-256 и размеру из manifest; R20 делает собственный SHA
**до и после** FFmpeg и проверяет, что указатель current всё ещё совпадает
с release_id/SHA master. Перечень сцен проверяется на уникальность ID,
корректность переходов и согласованность суммарной длительности с MP4 QA.
Разночтение завершается ошибкой, а не пустым PASS.

Перед декодированием FFprobe проверяет наличие видео, **одной AAC-аудиодорожки с двумя реальными каналами** и соответствие длительности. Моно и многоканальная исходная дорожка не приводятся незаметно к stereo: аудиопрофиль отказывает в выдаче отчёта.

Реальный H.264/AAC MP4 декодируется при помощи FFmpeg в 48 kHz stereo
signed 16-bit PCM. `screenRealStereoPcm` исследует последовательные
300-ms окна с фиксированными измерениями RMS, межканальной корреляции и
отношения Mid/Side. Помечает для прослушивания **возможную потерю голоса/музыки
при mono fold-down** или **возможный провал одного канала**, а не
автоматически исправляет звук. Каждое замечание имеет начало и конец
относительно *декодированного PCM потока*.

Ограничения: 60s / ~11.5 MB PCM, 128 MB входного MP4, timeout 90s.
Более длинное видео не принимается этим профилем, но это не запрет
на производство такого видео. Падения FFmpeg, изменение master/current
и несовпадение длины аудио приводят к ошибке. Проверка синхронизации
PCM с A/V PTS **не выполняется**; пользовательский seek — только приблизительный.

## Структура evidence

- `release_sha256`, `release_bytes` — фактически перепроверенные байты
  **master MP4**. `release_id` и `project_id` связаны с текущим P05.
- `source_scene_hashes` — хэши исходных сцен **из уже проверенного
  манифеста P05**, исходные файлы заново *не* хэшируются.
- `decoded_master_audio` — детерминированные рассчитанные метрики реального
  AAC-декодирования; `report_sha256` — хэш JSON для контроля случайной
  порчи, **не подпись и не доказательство личности issuer**.
- `cryptographically_signed:false`, `human_listening_verified:false`,
  `source_rights_verified:false`, `may_publish:false`,
  `may_deploy:false` — неизменные ограничения.

Анализ не определяет разборчивость речи, художественный замысел,
намеренную панораму, нормы громкости и права на исходники. Флаг
`manual_review_required:false` означает лишь, что эти *два грубых
электроакустических паттерна* не выявлены; он не эквивалентен QA PASS.

## Reproduce

```bash
node --test tests/cloud-real-master-audio-evidence.test.mjs
npm run test:cloud
npm run typecheck
npm run build
```

Тесты реально создают H.264/AAC MP4 через FFmpeg и сравнивают чистую
сборку с роликом, где один из стереоканалов инвертируется. `assembly`
в этих тестах является имитацией существующего серверного API, а не
полным E2E с директориальным P05, P08 и подписью.

## Следующий рубеж

Только после независимого QA и производственного ограничения нагрузок:
асинхронный worker/queue для анализа без блокировки HTTP, постоянное
хранилище результатов с привязкой к текущему release,
контроль доступа/подпись receipt, реальное ffprobe PTS-сопоставление,
верификация источников и права на просмотр. **Не** подключать синхронный
FFmpeg как обычный публичный GET route. Прямого вызова из QC-кокпита нет.
