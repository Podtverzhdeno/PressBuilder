# M58-R21 — изолированный worker, очередь и хранилище аудиоотчётов

**Статус: независимая реализация для ревью, production OFF.**
Наследует M58-R20 (PR #54), не изменяет P05 master и P07 review, не добавляет
публичный API и не подключает M51 UI. Автоматического публикационного
допуска нет.

## Контракт

- `realMasterAudioQueue({out,assembly,enabled:true})` хранит одновременный
  максимум **один** выполняющийся аудиоанализ, плюс ограниченный FIFO
  (`maxPending:3` по умолчанию). Дополнительные задания получают
  `M58_AUDIO_QUEUE_FULL` (429), не бесконтрольно занимают память.
- Используется отдельный `worker_threads.Worker`; синхронный FFmpeg
  из M58-R20 блокирует **только рабочий поток**, не Node HTTP event loop.
  Таймаут рабочего потока 110 секунд; каждый FFmpeg/FFprobe имеет собственный
  лимит времени, размера памяти и формата. Ресурсы могут разделяться с
  `createResourceGovernor` через `acquireResource` после включения в
  доверенный процесс.
- Выбор файла только через серверные `assembly.current(project)`,
  `assembly.download(project,release_id)`; worker получает *серверный*
  `out`, проверенные project/release ID и SHA. Он заново читает P05
  `current.json`, `manifest.json`, `final.mp4`; символические ссылки
  в этой цепочке запрещены. Ни HTTP-путь, ни FFmpeg-аргументы пользователя
  не принимаются.
- Перед запуском, **после ожидания ресурса** и после получения результата
  сверяются SHA и UUID текущего выпуска. Нельзя прикрепить старую диагностику
  к новому выпуску.
- `audio-audit-jobs/<project>.json` хранит статус/снимок SHA/UUID задания.
  `audio-audit-receipts/<project>/<sha>.json` — ровно один атомарно
  записанный отчёт по одному master SHA; существующий файл не
  перезаписывается. Все новые файлы с правами `0600`.
  `receipt_sha256` и `report_sha256` проверяются при чтении, но являются
  **контрольными хэшами, не криптографическими подписями issuer**.
- `enqueue` повторного задания для *того же* текущего релиза возвращает
  активный job или уже проверенный cached result; после смены релиза
  предыдущий отчёт помечается `stale` и не возвращается.
- После рестарта уже записанные `queued/running` переводятся в
  **FAILED / REQUIRES_REVIEW** и **не** запускаются автоматически:
  прежний процесс мог записать часть результата. Новое выполнение требует
  отдельного вызова `enqueue`; конфликтующий receipt не перетирается.
- `read(project)` выдаёт receipt только для текущего подтверждённого P05
  SHA и проверенного completed-джоба. Неиспользуемые старые receipts не
  дают прав на render, approve, merge, deploy или publish.

## Проверка

```bash
node --test tests/cloud-real-master-audio-queue.test.mjs
npm run test:cloud
npm run build
```

Тесты проверяют сериализацию, переполнение очереди, одинаковые запросы,
сбой рестарта, отсутствие replay, повреждение сохранённого JSON, смену
релиза во время работы, права файлов, cold read и **реальный** отдельный
worker: настоящий H.264/AAC MP4 с инверсией правого канала. В обычном CI
без FFmpeg реальный MP4-тест будет SKIP; в Docker CI с FFmpeg обязан PASS.

## Не выполнено

Это **не распределённая очередь**, не exactly-once across multiple servers
и не самостоятельная транзакционная DB. Требуется единственный process writer
(`flock` на общей Railway volume) и внешний governor для CPU/FFmpeg.
Промежуток между записью receipt и обновлением job status разрешается через
ручное reconciliation, а не перезапись. Работающий одновременно старый
процесс на другой реплике не блокируется этим модулем.

Пока нет authenticated REST/MCP endpoints и автоматического запуска на
production. Нельзя включать запуск на обычном GET или напрямую
`m58ReportLoader` синтетического M51-R03: форматы и доверенные источники
у M58-R19 и R20 **разные**. Для полноценного M51 требуется отдельный
верифицируемый адаптер реальных R20 receipts, авторизация, PTS A/V
alignment, проверка human review и независимый security review.
