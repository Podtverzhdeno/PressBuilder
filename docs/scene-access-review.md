# P06 + P07 — безопасная работа агентов и ревью по кадрам

## Граница доверия

**Текущий OAuth и общий `MCP_API_KEY` — полномочия director.** Не передавайте эти секреты производственным агентам: все владельцы общего ключа неразличимы для сервера и могут редактировать любые сцены. Для реальной изоляции используйте **уникальные bearer-ключи** в Railway env `PB_AGENT_KEYS_JSON`:

```json
{
  "Agent-01": {"role": "worker", "token": "<уникальный случайный секрет минимум 24 символа>"},
  "Agent-02": {"role": "worker", "token": "<другой случайный секрет минимум 24 символа>"},
  "QA-01": {"role": "reviewer", "token": "<ещё один отдельный секрет минимум 24 символа>"}
}
```

Секреты не коммитить. Генерация: `node -e "console.log(require('crypto').randomBytes(32).toString('base64url'))"`. Отдельный MCP-клиент каждого агента подключается к `https://<host>/mcp` со своим `Authorization: Bearer <token>`. Логины редактора по Basic Auth остаются director; локальный Vite работает в доверенном режиме. Роли: `viewer` — чтение; `worker` — аренда **только назначенной** сцены и запись только в неё; `reviewer` — замечания и подтверждение; `director` — назначение, общий проект, принудительный перехват.

**Не путать имя агента с правом:** `assignee` в задании сцены должен точно совпадать с ключом идентичности, например `Agent-01`.

## Порядок работы worker

1. Получить контекст проекта: `get_project_context`, `get_scene_task`.
2. Вызвать `claim_scene({"id":"demo","slide_id":"s01","ttl_seconds":600})`.
3. Хранить `lease_token` как секрет. При **каждом** вызове `set_scene_3d`, `set_scene_task`, `set_scene_checkpoint`, `update_cue`, `update_slide`, `update_object`, `set_slide_visuals`, `render_scene` передавать **оба** поля `lease_token` и `fencing_token`.
4. Пока идёт разработка, продлевать аренду `renew_scene_lease` до истечения TTL. Истёкшую аренду возобновить нельзя — требуется новый `claim_scene` и новый fencing token. После работы — `release_scene`.
5. Worker может менять сценовые визуальные элементы, статусы собственной задачи/чекпоинты, но не имена ответственных, глобальное README, текст озвучки, FPS, порядок сцен или утверждённый статус `done`.

При действующей аренде второго агента сервер возвращает конфликт. После истечения аренды или перехвата director все старые fencing/token-пары становятся невалидными. Логи действий в `/data/decks/<id>/.scene-audit/<scene_id>.jsonl`: actor, role, action, timestamp, trace_id (для записей), revision. Lease token и API-key не пишутся в audit.

**Ограничение:** файл-аренда пригодна для **одного процесса Node и общего долговременного тома**. При нескольких независимых инстансах или multi-region используйте PostgreSQL с транзакционным claim/CAS и monotonic fence (иначе гарантировать эксклюзивность нельзя). Долговременная отзывность OAuth per-agent пока отсутствует — существующий OAuth выдает director, поэтому для изоляции рекомендованы отдельные bearer-key подключения.

## Цикл ревью кадра

1. Дождаться `render_scene` → `get_scene_render_status.status=completed`; сохранить `job_id`, FPS и длительность.
2. В редакторе открыть **Ревью кадра** → выбрать сцену и остановить MP4 в нужный момент (например 3,400 с).
3. По необходимости нажать **Выделить область**, нарисовать рамку поверх кадра, написать проблему и выбрать серьёзность.
4. `create_scene_review_item` (reviewer/director) сохраняет `render_revision=job_id`, `t` (секунды **от начала сцены**), `fps`, `frame=round(t*fps)`, координаты в долях `[0,1]` и опциональную уменьшенную JPEG-миниатюру.
5. Worker читает `list_scene_review_items` и `get_scene_review_item`, исправляет сцену в рамках аренды, затем делает `update_scene_review_item(status="FIXED",note=...,expected_revision=...,lease_token=...,fencing_token=...)`.
6. Reviewer/Director просматривает исправленный рендер и ставит `VERIFIED`, либо `REOPENED` с пояснением. Изменения истории не удаляются; для одновременных правок используется optimistic revision (409).

**Ограничение P08:** thumbnail и версия исходного рендера, к которой относится комментарий, сохраняются, но **старый MP4 пока не архивируется** — после нового рендера скачать старый ролик может быть невозможно. Не путать сохранённую миниатюру с полным сохранением версии видео. Ручная художественная приёмка обязательна.

## Проверки

```bash
npm ci
npm run build
npm run test:cloud
```

В `tests/cloud-scene-access-review.test.mjs` проверяются права разных учётных данных по HTTP, чужие сцены, отсутствие аренды, fencing, TTL, перехват, сохранение изображения, таймкод/FPS, контроль переходов и история исправлений.

## Остаточные задачи перед полным DoD

- Scoped OAuth/credential issuance для нескольких ChatGPT-клиентов; изоляция через общий owner OAuth **невозможна**.
- Транзакционная lease-таблица при развёртывании нескольких реплик Railway.
- Сохранение неизменяемого исходного MP4/manifest и открытие старых роликов (P08).
- Реальный браузерный E2E двух пользователей с рендером и screenshot/review, а также мониторинг объёма evidence/audit.
