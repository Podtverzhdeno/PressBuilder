# Задания по сценам: параллельная работа AI-агентов

## Новый агент в пустом чате: README → ТЗ → чекпоинты

В каждом видеопроекте PressBuilder есть **отдельный Markdown README.md**, который задаёт общую концепцию, стиль, технические параметры, правила работы и карту сцен. Это **не** корневой README репозитория PressBuilder.

- Локально: `src/decks/<project-id>/README.md`.
- Railway: `/data/decks/<project-id>/README.md` на постоянном томе.
- Если проект поставляется вместе с GitHub-репозиторием, `src/decks/<id>/README.md` и `src/decks/<id>/.scene-tasks/sNN.json` служат **исходными заданиями**. После правки через чат изменения идут в `/data/decks/...` и не изменяют GitHub; новая версия README или сцены в GitHub не перезатрёт прогресс агента в постоянном томе.
- Пример исходного README и задания: `src/decks/a2a-3d-hero/README.md` и `src/decks/a2a-3d-hero/.scene-tasks/s01.json`.
- Новые проекты получают README автоматически. Существующие без файла видят корректный сгенерированный обзор; после редактирования он сохраняется как файл.
- В редакторе кнопка **«README проекта»** открывает содержимое Markdown для правок.
- README не хранится в `deck.json`; задания и чекпоинты — тоже отдельные файлы.
- Для обновления README нужно `expected_revision`: если другой агент уже изменил документ, сервер возвращает **409**, старое содержимое не перезаписывается.

**Один вызов для старта**: `get_project_context({"id":"my-video","slide_id":"s01"})`. В ответе README, метаданные проекта, сводка задач, назначение и полные чекпоинты сцены `s01`. Если ID неизвестен — сначала `list_decks`. Можно вызвать `get_project_context` без `slide_id`, чтобы получить карту всех сцен.

Отдельные MCP-инструменты:

- `get_project_readme` — прочитать README.md конкретного проекта
- `update_project_readme` — сохранить изменённый Markdown с актуальной ревизией
- `get_scene_task` — прочитать подробное ТЗ конкретной сцены

**Пример начала в совершенно новом чате:**

> Подключись к PressBuilder. Найди проект «Название ролика» с помощью list_decks. Прочитай его README через get_project_context, затем прочитай задачу для s03 через get_scene_task. Кратко изложи требования и невыполненные чекпоинты и начни работу только над s03.

### Область действия

README — общий контракт проекта; `get_scene_task` — постановка задачи конкретному агенту; `get_deck` — фактические параметры ролика и текст реплик. Если поля не заполнены, агент не должен притворяться, будто ТЗ существует.

## Что реализовано

У каждого проекта PressBuilder и каждой сцены есть независимое задание. Откройте ролик в веб-редакторе и нажмите **«Задания агентам»**. В левой колонке — все сцены, исполнители, статусы и прогресс, справа — подробное ТЗ, критерии приёмки, чекпоинты и примечания. Можно заполнить стандартные пять этапов, добавлять/удалять собственные и копировать готовый промпт агенту.

Хранилище отделено от `deck.json`:

- локально: `src/decks/<project-id>/.scene-tasks/<scene-id>.json`;
- в Railway: `/data/decks/<project-id>/.scene-tasks/<scene-id>.json` (постоянный volume);
- на каждый слайд — отдельный JSON, изменения одной сцены не переписывают чужие;
- общий `deck.json` по-прежнему отвечает за текст, тайминг и визуальное содержимое, но **не** хранит задания;
- поле `revision` защищает от перезаписи более свежего ТЗ старым сохранением: сервер отвечает HTTP 409.

Для всех существующих проектов без задач автоматически возвращается пустое задание на каждый слайд. Ничего мигрировать не требуется.

## MCP для агента

1. `get_deck({"id":"my-video"})` — открыть ролик; в `scene_tasks` есть краткие статусы, исполнители и счётчики чекпоинтов.
2. `list_scene_tasks({"id":"my-video"})` — получить все полные задания, в том числе ТЗ, критерии, чекпоинты.
3. `get_scene_task({"id":"my-video","slide_id":"s01"})` — прочитать своё задание и актуальную `revision`.
4. `set_scene_task({"id":"my-video","slide_id":"s01","expected_revision":0,"assignee":"Agent-01","title":"3D Hero","brief":"...","deliverables":"...","status":"in_progress","checkpoints":[{"id":"model","title":"3D-модель готова","done":false}]})` — назначить агента или отредактировать ТЗ. При конфликте заново прочитать и повторить.
5. `set_scene_checkpoint({"id":"my-video","slide_id":"s01","checkpoint_id":"model","done":true,"note":"Ссылка на MP4 и результат проверки"})` — отметить один выполненный этап. Остальные сцены и чекпоинты не затрагиваются.

Состояния: `todo` → `in_progress` → `review` → `done`, также `blocked`.

## HTTP API (редактор)

Все маршруты защищены текущей авторизацией веб-редактора:

| Метод | Путь | Действие |
| --- | --- | --- |
| GET | `/api/decks/:id/tasks` | Все задания проекта |
| GET | `/api/decks/:id/tasks/:scene` | Полное задание сцены |
| PUT | `/api/decks/:id/tasks/:scene` | Частичное изменение полей задания, обязательна `expected_revision` |
| PATCH | `/api/decks/:id/tasks/:scene/checkpoints/:checkpoint` | Изменение `done` и/или `note` одного этапа |

## Пример распределения 6 агентов на 6 сцен

Общий master-контракт для всех: формат 16:9, одинаковый FPS и цветовая система, минимальный текст, общие правила содержания, согласованные переходы и единый принцип именования артефактов. Не изменять соседние сцены или чужие задания.

| Агент | Сцена | Результат |
| --- | --- | --- |
| Agent-01 | s01 — 3D Hero | Объёмное ядро сделки, камера orbit, свет, титр |
| Agent-02 | s02 — RFQ/Quote | Переговоры buyer/supplier, поток предложений |
| Agent-03 | s03 — A2A ≠ Payment | Разделение коммуникаций и банковского исполнения |
| Agent-04 | s04 — Authorization | Проверки полномочий, лимитов, подписей |
| Agent-05 | s05 — DLT | Проверяемое событие, hash(doc), deal_id, state |
| Agent-06 | s06 — Settlement | Поставка, приёмка, платёж, подтверждение банка |

Каждое задание может быть произвольно подробным (до 20 000 символов). Указывайте обязательные 3D-ассеты, композицию, траекторию камеры, шейдинг, анимацию по секундам, переходы, сроки и критерии приёмки. Чекпоинты отмечайте **только после выполнения и проверки**, прикладывайте ссылку на артефакт и результат теста.

## Ограничения и будущие улучшения

- Реализованы отдельные задания, чекпоинты и API для параллельного ведения. **Это не автоматический запуск шести агентов** — запуск и сборку видео должен выполнять внешний оркестратор.
- Внутри одного и того же задания несколько писателей должны повторять запрос после HTTP 409. Для двух параллельных обновлений одного чекпоинта полноценной межпроцессной блокировки пока нет; рекомендуем назначать **одного владельца на сцену**.
- Статус `done` выставляется исполнителем или координатором, не является автоматическим доказательством успешного рендера.
- Внешние файлы и исходники хранятся отдельно; в `note` чекпоинта можно приложить путь или ссылку.

## P08/P09: версионирование и временные события для агента сцены

Перед записью сцены прочитай `get_scene_sync({id,slide_id})`: вернётся шкала времени реплик и текущие motion/audio cues. Если метки сцены отсутствуют, можно создать свои `beat` / `animation` / `camera` / `sfx` события с привязкой к стабильному `cue_id`, а не фиксированной секунде.

Worker обязан получить `claim_scene` и передавать действующий `fence_token` при `set_scene_sync`, `set_scene_3d` и записи чекпоинтов. При конфликтах revision перечитать соответствующее задание и повторить только после проверки чужих изменений.

Для синхронного появления 3D-модели укажи в её объекте `start_marker: "имя-маркера"`. Тогда после изменения длительности реплики начало появления автоматически следует за cue anchor. Не допускается отмечать сцену готовой, пока `get_scene_sync` показывает `validation_error` или объект 3D ссылается на неизвестный маркер.

После `render_scene` проверь `get_scene_render_status`, `get_scene_qa_report` и `list_scene_versions`. Приёмка MP4 и восстановление исторически одобренной версии управляются директором, учитывают P07 frame reviews; не объявляй релиз успешным без утверждения. Звуковые SFX/music markers пока не означают, что музыка реально включена в MP4 — требуются отдельные аудиодорожки и mixer.
